# 前端联调指南

适用后端：`0.2.0`；更新：2026-11-04。

## 获取并独立运行后端

前端开发者可在自己的电脑另外克隆一份后端，使用独立的数据库和个人 Key，不依赖另一位开发者的电脑持续开机：

```sh
git clone --branch backend https://github.com/Qiiii1/team-develop.git team-develop-api
cd team-develop-api
npm ci
npm start
```

需要 Node.js `>=22.9.0`。全新克隆未配置证书时，默认入口为 `http://localhost:4185`；已有 `.env.web.local` 的机器按终端实际打印的 HTTP / HTTPS 地址访问。`GET /health` 返回 `{"ok":true}`。

`backend` 分支包含后端与 `web/` 参考实现。`frontend` 分支此前已按要求清空，需由前端开发者提交自己的项目；GitHub 上的分支不会自动建立运行时连接。不要把两条分支互相完整覆盖，交付时按实际改动合并和审查。

## 方式一：同源开发代理（推荐）

让浏览器请求前端自身的 `/api/v1/...`，由前端开发服务器将 `/api` 代理到本机后端。浏览器看到的是同源请求，沿用 Cookie + CSRF，不需要为前端另开跨域 Bearer 登录。

以下为使用 Vite 的前端示例，配置放在**前端项目**；后端不依赖 Vite，也不会因此新增依赖：

```js
// vite.config.js
import { defineConfig } from 'vite';

export default defineConfig({
  server: {
    host: '127.0.0.1',
    port: 5173,
    strictPort: true,
    proxy: {
      '/api': {
        target: 'http://localhost:4185',
        changeOrigin: false,
      },
    },
  },
});
```

前后端均为本机 HTTP 时，浏览器打开 `http://localhost:5173`，前端的 API 基地址留空。`changeOrigin: false` 保留前端 Host，使后端同源校验和浏览器 Origin 一致；后端默认允许 `localhost` 和 `127.0.0.1`。整个登录流程统一使用同一个主机名。

若后端已经配置 HTTPS，则代理目标也要改为 HTTPS，**前端开发服务器也使用 HTTPS**，以匹配后端的协议检查和 Secure Cookie；让代理运行进程信任后端 CA，例如启动前端时设置 `NODE_EXTRA_CA_CERTS=/你的公开CA路径/ca.pem`。证书域名必须匹配代理目标。局域网真实密码与 Key 使用 HTTPS，配置见[局域网 HTTPS](局域网HTTPS配置.md)。

同源请求规则：

```js
const response = await fetch('/api/v1/teams', {
  credentials: 'same-origin',
});
```

注册或登录响应会返回 `csrfToken` 并设置 HttpOnly Cookie。后续 `POST / PUT / PATCH / DELETE` 带 `Content-Type: application/json`、`X-CSRF-Token` 和 JSON 请求体；无业务字段的写操作也发送 `{}`。刷新页面先请求 `GET /api/v1/me` 恢复身份与 CSRF token。不要读取或自行保存 HttpOnly Cookie。

## 方式二：浏览器直接跨域连接 API

现有后端启动配置只允许显式列出的 **HTTPS Origin**。例如前端为 `https://localhost:5173`，在后端 `.env.web.local` 配置：

```dotenv
HARNESS_WEB_ALLOWED_ORIGINS=https://localhost:5173
```

多个来源使用逗号分隔；Origin 包含协议、主机、端口，不含路径或末尾 `/`，不能填写 `*`。修改后重启后端。前端、后端证书均需有效并受信任；前端 HTTPS 直接连接普通 HTTP API 可能被浏览器拦截，应使用 HTTPS 后端。

直接跨域使用 Bearer **网站会话**，与成员的模型 API Key 是两种不同凭据：

1. 包括注册／登录在内，每次请求都带 `X-Harness-Session: bearer`，使用 `credentials: 'omit'`。
2. 注册／登录响应额外返回 `sessionToken`，保存到当前标签页的 `sessionStorage`。
3. 后续请求带 `Authorization: Bearer <sessionToken>`；不要把模型 API Key 放到这个请求头中。
4. 退出登录调用后端退出接口，再清除本地会话。收到 `401` 时清除身份并回到登录页。

可参考现有实现 `web/app.js` 的 `api()`。新前端示例：

```js
const API_BASE = 'https://localhost:4185'; // 不包含 /api/v1
const SESSION_KEY = `team-develop:${API_BASE}:session`;

async function api(path, { method = 'GET', body } = {}) {
  const session = sessionStorage.getItem(SESSION_KEY);
  const response = await fetch(`${API_BASE}/api/v1${path}`, {
    method,
    credentials: 'omit',
    headers: {
      'X-Harness-Session': 'bearer',
      ...(session ? { Authorization: `Bearer ${session}` } : {}),
      ...(method !== 'GET' ? { 'Content-Type': 'application/json' } : {}),
    },
    ...(method !== 'GET' ? { body: JSON.stringify(body ?? {}) } : {}),
  });
  if (response.status === 401) sessionStorage.removeItem(SESSION_KEY);
  if (!response.headers.get('content-type')?.includes('application/json')) {
    throw new Error('API 未返回 JSON，请检查地址或代理配置。');
  }
  const data = await response.json();
  if (!response.ok) throw new Error(data.error || `请求失败：${response.status}`);
  if (data.sessionToken) sessionStorage.setItem(SESSION_KEY, data.sessionToken);
  if (path === '/auth/logout') sessionStorage.removeItem(SESSION_KEY);
  return data;
}

await api('/auth/login', {
  method: 'POST',
  body: { username: '你的登录名', password: '你的密码' },
});
const { teams } = await api('/teams');
```

同源和跨域机制应按部署方式选择；同源来源不能发送 Bearer Authorization。后端在跨域 Bearer 模式下不要求 CSRF token，现有参考前端同时发送该头也可兼容。

## 建议对接顺序

| 步骤 | 接口与验收 |
| --- | --- |
| 1. 身份 | 注册、登录、`GET /me`、退出；刷新可恢复身份，退出后不可继续读取 |
| 2. 团队 | 创建、列表、详情、邀请、加入、成员；双账号能进入同一团队 |
| 3. 配置 | 获取自己的 AI 配置，携带 `revision` 保存／删除；Key 不回显 |
| 4. 公共讨论 | 普通消息不调用 AI；明确 `@AI` 使用发送者自己的 Key |
| 5. 私人对话 | 创建、列表、发问、翻页；另一账号不能读取私人 thread |
| 6. 成果 | 编辑和预览都在前端完成，本人确认后才调用发布接口 |
| 7. 资料版本 | 提出草案、指定确认人处理、显示生效／待确认／退回与冲突 |
| 8. 管理后台 | 仅 `isSystemAdmin` 显示入口，接口仍由后端校验权限 |

完整参数与响应见[API 接口文档](API.md)。不要在前端直接调用 DeepSeek；个人 Key 通过个人配置接口交给后端。

## 状态与常见问题

- AI 请求非流式，最长等待约 60 秒，前端请求超时应留出余量。HTTP `200` 不代表 AI 成功，检查 `prompt.aiStatus` 和 `aiError`。网络超时后先查消息状态或用原 `requestId` 查询同一次提交，不自动生成新编号重试模型。
- 当前讨论和个人消息可每 4 秒查询一次，隐藏标签页暂停。尚无 WebSocket / SSE；分享和资料版本按需刷新。
- `409` 可能表示版本变化、请求编号冲突、AI 正在处理、团队停用或未配置 Key，需按 `error` 提示处理。刷新版本后由用户确认再提交，不能盲目覆盖。
- `403 请求来源未获授权`：检查协议、Origin 端口、后端允许列表，以及代理是否保留 Host；跨域记得 `X-Harness-Session`。
- `401`：没有登录、会话过期、被强制退出或账号停用；普通会话有效期 7 天。
- `404`：同时可能表示资源不存在或无权读取，不能据此推断他人的资源是否存在。
- 队友浏览器里的 `localhost` 指向队友自己的电脑。连接另一台电脑的服务需要 LAN 地址、网络互通和证书信任。
- GitHub Pages 当前为静态预览，业务请求关闭；没有启用公网隧道。部署网页不等于部署后端。

## 协作与提交

后端接口变更和对应文档一起提交到 `backend`。前端开发者更新自己的后端副本：

```sh
git switch backend
git pull --ff-only origin backend
npm ci
npm start
```

先停止旧服务再启动；启动会应用迁移。各自的 `.local/` 和真实环境文件不互传、不提交。前端项目放在独立目录／工作副本中，避免切换到空的 `frontend` 分支影响正在运行的后端。
